# BUILD_NOTES 编写标准

每个编译任务必须维护 `/work/output/BUILD_NOTES.md`（现场记录，工单与经验沉淀的原料）。

## 更新节奏（强制）

1. **开工建骨架**：源码就绪、探测完环境后，第一次 write_file 就建完整模板骨架（各节标题+环境探测结果）。此后任何时刻文件都存在——任务中途被杀时，骨架+前几段就是"死在哪一步"的证据。
2. **分段更新**：每过一个里程碑就重写补全对应节——依赖装完 / configure 完成 / 编译中受挫与绕行 / install / 打包 / 验证。**"踩坑与修复"节实时记录**：每次失败-分析-换路都追加一条（症状→根因→处置），不要攒到最后凭记忆补。
3. **收尾必写**：无论成败都要完成"验证/已知限制"节。失败时重点写结论段：死在哪步、试过哪些路线、下一步建议。
4. **多轮重试**：第二轮起在文末追加 `## Attempt 2` 段记录本轮路线，前轮内容保留不删。

## 模板骨架

```markdown
# <软件名> 编译记录（BUILD_NOTES）

## 环境
<!-- 系统/内核、gcc/g++ 版本、python/node 版本、cmake/ninja/make 版本 —— 全部来自实际探测命令，不是文档抄录 -->

## 依赖
<!-- 实际执行的安装命令原样粘贴（dnf/pip/npm 整行），含来源镜像/版本号；标注哪些是预装、哪些是新装 -->

## 步骤
<!-- 编号列出实际执行的关键命令，每条标注结果：✅ 成功 / ⚠ 重跑或绕行 / ❌ 失败及去向 -->

## 与所读 SKILL 的差异
<!-- 本节最有价值。对照你 read_file 读过的攻略 SKILL.md，实测与文档不符处逐条列出：
     文档说 X，实测是 Y（原因/正确做法）。没读攻略或完全一致也写明 -->

## 踩坑与修复
<!-- 三段式：症状（报错原文关键行）→ 根因 → 处置。包括静默慢命令、重试、回退方案 -->

## 耗时
<!-- 各阶段实测（clone/依赖/configure/编译/install/打包/验证）；估算值标注"约" -->

## 验证
<!-- 做了什么验证动作、看到什么输出。格式："动作 → 结果"。例：干净 venv pip 装 wheel → import 成功、矩阵乘 42.3。
     不记产物字节数/文件 hash（文件系统自答） -->

## 已知限制
<!-- 关闭的特性、未做的优化、依赖的外部条件、仅适配特定版本等 -->
```

## 篇幅要求

- 常规任务按模板写全（目标 60-150 行）
- **简单包豁免**：单条命令就编完的小项目（hello 级），写 10 行以内的精简版（环境/步骤/验证三节即可），不要凑作文
- 中文书写；报错原文保留英文

## 反面清单（别写这些）

- 从 SKILL/文档复制粘贴的"步骤"（必须是实际执行过的命令）
- 产物大小/sha256/md5 之类的文件属性
- "一切顺利"式空洞总结（验证节要有具体动作和具体输出）
